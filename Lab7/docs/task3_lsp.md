# Завдання 3. Liskov Substitution Principle (LSP) — Варіант 3

**Предметна область:** геометричний графічний редактор (Rectangle / Square).
**Код:** `src/shapes/` (рефакторинг), `src/shapes/legacy/` (вихідний код), демо — `ShapesDemo`.

## 1. Виявлене порушення контракту

Вихідна ієрархія: `Square extends Rectangle`, де `Square` перевизначає `setWidth` та `setHeight` так, що зміна однієї сторони змінює й другу.

| Елемент контракту `Rectangle` | Що обіцяє базовий тип | Що робить `Square` |
|---|---|---|
| Постумова `setWidth(w)` | `width == w` **і `height` не змінилась** | `height` теж стає `w` — постумова послаблена |
| Постумова `setHeight(h)` | `height == h` **і `width` не змінилась** | `width` теж стає `h` — постумова послаблена |
| Інваріант | `width` і `height` незалежні | `width == height` завжди — інваріант підміняється |

### Чому підстановка ламає клієнта
`AreaCalculator.resizeAndVerifyArea(Rectangle rect)` робить `setWidth(5); setHeight(10)` і очікує площу `5 × 10 = 50`.
- `Rectangle` → площа 50, усе гаразд.
- `Square` → після `setHeight(10)` обидві сторони = 10, площа **100**, клієнт кидає `RuntimeException("LSP Violation detected!")`.

Клієнт не змінювався, змінився лише підтип — це і є порушення LSP. Типова "математична" відповідь «квадрат — це прямокутник» тут не працює: у **змінюваних** об'єктів значення має значення поведінка, а не геометрія.

## 2. Рефакторинг

Застосовано два прийоми з вимог лабораторної: **розділення ієрархії** та **незмінні Value Objects із Guard Clauses**.

```
          «interface» Shape
              + area()
             /          \
   Rectangle (final)   Square (final)
   width, height       side
```

1. `Square` більше **не наслідує** `Rectangle`. Спільне між ними — лише `Shape.area()`, тільки цей контракт безпечно підставляється.
2. `Rectangle` і `Square` — **immutable Value Objects** (`final` клас, `final` поля, без сеттерів). Зміна розміру = створення нового об'єкта: `rect.withWidth(5).withHeight(10)`. Сценарій "змінив одну сторону — зламалась інша" став неможливим за побудовою.
3. **Guard Clauses** у конструкторах (`Guard.positiveFinite`) — інваріант `розмір > 0, скінченний, не NaN` перевіряється одразу при створенні (**Fail-fast**). Некоректний об'єкт неможливо створити, тому в жодному місці коду не потрібні повторні перевірки.
4. `AreaCalculator.resizeAndVerifyArea` приймає саме `Rectangle`: спроба передати `Square` дає **помилку компіляції**, а не збій у рантаймі.
5. `AreaCalculator.totalArea(List<? extends Shape>)` — приклад **безпечної** підстановки: працює з будь-якою фігурою через спільний контракт.

## 3. Підтвердження (вивід `ShapesDemo`)
- Legacy: `Rectangle: OK`, `Square: ЗБІЙ -> Expected area 50.0, but got 100.0`.
- Refactored: площа після resize = 50; вихідний `Rectangle(2,3)` не змінився; `totalArea(Rectangle 5x10 + Square 3) = 59`; `Rectangle(-1,5)`, `Rectangle(0,5)`, `Square(NaN)`, `withWidth(-3)` → `IllegalArgumentException`.

## 4. Що казати на захисті
- **Чому не просто перевірити `instanceof Square` у клієнті?** Це порушує ще й OCP: клієнт знає про всіх нащадків, і кожен новий підтип вимагає правки клієнта.
- **Чому не зробити `Rectangle` extends `Square` або спільний абстрактний клас із `setWidth`?** Сеттери в спільному предку знову нав'язують "дві незалежні сторони" фігурі, яка має одну.
- **Чи не втрачено щось?** Ні: `Square` має власний, чесний API (`side()`, `withSide()`), а все, що справді спільне, винесено в `Shape`.
- **Яка форма LSP дотримана?** Нема послаблених постумов, нема посилених передумов, нема винятків, яких не очікує базовий тип, інваріанти збережено.

## 5. Внесок у Завдання 6 (для `task6_dry_kiss_yagni.md`)
- **DRY:** правило «розмір — скінченне додатне число» живе в одному місці (`Guard.positiveFinite`) і використовується в `Rectangle` та `Square`.
- **KISS:** немає перевірок `instanceof`/приведення типів у клієнті; немає складних сеттерів із побічними ефектами — усе зведено до конструктора з Guard Clause та простих `withXxx`.
- **YAGNI:** додано тільки `Shape`, `Rectangle`, `Square`, `Guard`, `AreaCalculator`. Немає фабрик, візитерів чи `Shape.scale()` "на майбутнє"; немає `NotImplementedException` та методів-заглушок.
